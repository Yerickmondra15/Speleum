# Plan de trabajo de Speleum — 6 de agosto de 2026

## Objetivo de hoy

Cerrar la noche con una base más confiable y un camino técnico claro. Hoy no conviene agregar sonidos, skins, decoraciones ni criaturas nuevas. Primero se debe impedir que el ranking sea manipulable, definir identidad segura en sockets, preparar reconexión y establecer pruebas repetibles.

## Estado inicial

### Completado durante la auditoría

- Revisión de arquitectura, diseño del juego y mejoras futuras.
- Contraste de la documentación con el código de `main`.
- Identificación de riesgos de resultados, sockets, reconexión, sesiones y validación.
- Creación de una rama independiente para no tocar `main` directamente.
- Creación de auditoría técnica detallada.
- Creación de `.env.example`.

## Bloque 1 — Integridad de resultados

### Meta

Evitar que el cliente pueda inventar puntuación, ganador o fechas.

### Trabajo

1. Crear esquema de validación de la petición de resultados.
2. Permitir únicamente modos, estados, resultados y criaturas conocidos.
3. Rechazar puntuaciones negativas o fuera del máximo razonable.
4. Rechazar fechas inválidas o partidas con duración imposible.
5. En multijugador, dejar de confiar en `winnerId` enviado por cada navegador.
6. Diseñar guardado autoritativo desde Socket.IO o mediante comprobante firmado.
7. Garantizar idempotencia por `matchId + userId`.

### Criterios de terminado

- Alterar `scoreEarned` desde DevTools no aumenta libremente el ranking.
- Un perdedor no puede declararse ganador.
- Repetir la petición no duplica partidas ni estadísticas.
- Los errores devuelven mensajes y códigos HTTP claros.

## Bloque 2 — Identidad y reconexión multijugador

### Meta

Relacionar cada socket con un usuario real y permitir recuperar una partida tras una caída breve.

### Trabajo

1. Crear una API autenticada que emita un ticket temporal para Socket.IO.
2. Validar ese ticket al conectar el socket.
3. Asociar `socket.data.userId` al jugador de la sala.
4. Crear token o flujo `resume-room`.
5. Cambiar desconexión inmediata por estado temporal `disconnected`.
6. Mantener posición, vida, cooldowns y sala durante 20–30 segundos.
7. Eliminar o marcar derrota únicamente después de vencer la gracia.
8. Impedir dos conexiones activas con la misma identidad en la misma sala.

### Criterios de terminado

- Recargar la pestaña o perder conexión unos segundos no elimina al jugador.
- El jugador recupera exactamente su vida, posición y estado.
- Un tercero no puede apropiarse de su jugador con solo conocer el código de sala.

## Bloque 3 — Ciclo de vida de salas

### Meta

Evitar memoria acumulada y estados abandonados.

### Trabajo

1. Añadir `lastActivityAt` a la sala.
2. Limpiar salas vacías inmediatamente.
3. Limpiar salas terminadas después de un plazo corto.
4. Cerrar salas de lobby abandonadas por inactividad.
5. Registrar métricas básicas en logs: creación, inicio, final, desconexión y limpieza.
6. Documentar que el MVP requiere una sola instancia del servidor de sockets.

### Criterios de terminado

- Una sala terminada no permanece indefinidamente en memoria.
- Una sala vacía desaparece.
- Los logs permiten reconstruir el flujo de una partida fallida.

## Bloque 4 — Pruebas y CI

### Meta

Detectar regresiones antes de desplegar.

### Trabajo

1. Añadir Vitest para lógica pura.
2. Crear scripts `typecheck`, `test` y `test:run`.
3. Probar rutas, alcance de ataque, parry, daño, stun y señales.
4. Probar generación procedural determinista por semilla.
5. Añadir pruebas de integración de Socket.IO para sala, ready, inicio, salida y reconexión.
6. Crear workflow de GitHub Actions con Node 20.
7. Ejecutar lint, tipos, pruebas y build en cada PR.

### Criterios de terminado

- `npm run lint` pasa.
- `npm run typecheck` pasa.
- `npm run test:run` pasa.
- `npm run build` pasa.
- GitHub muestra una verificación automática por cada PR.

## Bloque 5 — Prueba manual de cierre

### Flujo mínimo

1. Registrar usuario.
2. Verificar correo.
3. Iniciar sesión con segundo factor.
4. Seleccionar criatura.
5. Completar una partida local.
6. Confirmar una sola actualización de perfil y ranking.
7. Crear sala con dos navegadores.
8. Confirmar ready-check e inicio.
9. Probar movimiento, ataque, parry y radar.
10. Cortar conexión de un navegador y reconectar dentro de la gracia.
11. Terminar la partida y confirmar resultados correctos para ambos.
12. Reiniciar frontend y servidor por separado para confirmar mensajes de error claros.
